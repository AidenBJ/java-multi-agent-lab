S2.5错误恢复：三条恢复路径

模块：error-recovery

1. 这个模块解决了什么

调 LLM 会失败——429 限流、529 过载、413 prompt 太长。不能一失败就崩，要自动恢复。

2. 三条恢复路径

路径 1（退避重试）：429/529 指数退避——min(500×2^attempt, 32000)+jitter，最多 10 次。
路径 2（切备用模型）：连续 3 次 529，切到备用模型（如 DeepSeek → GLM）。
路径 3（压缩重试）：413 prompt_too_long，压缩上下文后重试一次。

3. 逻辑流程

调 LLM 失败
   ↓
ErrorClassifier 分类错误类型
   ↓
429/529 → 退避等待 → 重试（最多10次）
   ↓ 连续3次529
切备用模型
   ↓
413 → 压缩上下文 → 重试一次

4. 关键设计

恢复动作注入而非 new（压缩/切模型用回调注入，桩测试记录调用次数）。
错误分类做成纯函数，离线可测。

🚀 初学者快速上手

前置知识：知道 HTTP 状态码（429/529/413 是什么意思）。
核心概念一句话：调 LLM 失败了不要直接崩，退避重试/切模型/压缩上下文再试。
离线可测：桩测试记录调用次数，不调真实 LLM。

5. 运行命令

mvn -q -pl error-recovery exec:java "-Dexec.mainClass=com.example.agentlab.errorrecovery.RecoveryDemo"
Phase 2 收尾：规划/子Agent/记忆/压缩/恢复——单 Agent 的复杂任务能力齐了。
