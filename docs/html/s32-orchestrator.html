S3.2Orchestrator-Worker：拆解→并行→聚合

模块：orchestrator

1. 这个模块解决了什么

"做行业调研"——市场规模、竞品、用户画像三件事互不依赖。Orchestrator 拆成 N 个并行子任务，全做完后聚合。

2. 图结构（fan-out / fan-in）

START → orchestrator(拆任务) ──fan-out──→ worker0 / worker1 / worker2
                                                  │
                                            fan-in ↓
                                          aggregator(聚合) → END

3. 重要实测发现

实现实测耗时结论
图 fan-out/fan-in 结构版954ms≈ 串行 3×300ms，串行遍历分支
虚拟线程节点内部并行版306ms≈ 单个 worker，真并行 ~3x
结论：langgraph4j 1.8.27 的 fan-out 是串行遍历的。真并行下沉节点内部用 Java 21 虚拟线程。

4. 关键代码（虚拟线程并行）

try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = subtasks.stream().map(pool::submit).toList();
    return futures.stream().map(Future::get).toList();  // fan-in
}

5.5 核心类详解

OrchestratorDemo（演示入口）

作用：启动 Orchestrator 模式演示，对比串行 vs 并行耗时。

OrchestratorGraph（编排图）

作用：编排模式的状态机，控制拆解→并行→聚合流程。

方法：
方法作用输入输出
run(String task)执行任务任务描述聚合后的结果

TaskSplitter（任务拆解器）

作用：把大任务拆成多个子任务。

ParallelWorker（并行工人接口）

作用：定义工人执行子任务的接口。

Aggregator（聚合器接口）

作用：把多个结果聚合成一个。

🚀 初学者快速上手

前置知识：理解 fan-out/fan-in（一个拆多个，多个汇一个）。
核心概念一句话：大任务拆成并行子任务，全做完后聚合。
实测对比：跑 OrchestratorDemo（954ms）和 VirtualParallelDemo（306ms），看真并行差多少。
